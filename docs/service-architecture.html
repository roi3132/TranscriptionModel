Start here: three responsibilities

The API accepts files and serves job resources. PostgreSQL owns job state and results. The worker executes decoding and inference outside HTTP. Redis connects submission to execution by carrying job IDs, not media bytes or transcripts.

HTTP contract

Short request, durable work

Accepted work returns 202 after upload persistence and submission policy. Clients poll the job and fetch its result later; HTTP does not wait for inference.

Source of truth

PostgreSQL owns state

Redis transports job IDs, but PostgreSQL decides whether a job is queued, claimed, retryable, complete, failed, or expired.

Execution boundary

One terminable child per attempt

The supervisor launches a fresh child process so a hard timeout can terminate native FFmpeg/CTranslate2 work and reclaim its memory safely.

Media behavior

Normalize before inference

PyAV decodes the first audio stream, resamples it to signed 16-bit 16 kHz mono PCM, and creates ordered WAV chunks.

Reliability

Leases, retries, checkpoints

Job attempts use renewable leases and exponential backoff. Completed chunks are checkpointed atomically so a later attempt can resume.

Deployment

No hosted dependency required

API, worker, PostgreSQL, Redis, media, and model cache all run locally through Docker Compose and named volumes.

Most important invariant: a new job's media and authoritative database row are persisted before acceptance. The API's lifetime does not own the accepted work. A reused completed job can already have its result stored and source media deleted.

Runtime topology: four services, two paths

Compose runs four services. The API and worker share only generated-key media storage and infrastructure connections; model weights are mounted only into the worker.

Submission: admission, persistence, and reuse

Upload admission is intentionally layered. Cheap transport rejection happens first; authoritative persistence and deployment-wide queue admission happen afterward.

  1. Rate admission. A process-local sliding window checks the socket client address. The default is 10 submissions per 60 seconds.
  2. Upload capacity. An AnyIO capacity limiter admits at most two upload parsers per API process by default.
  3. Transport bounds. Declared and streamed request bytes are capped at the file limit plus 64 KiB of multipart overhead.
  4. Multipart policy. Starlette accepts one file and three small form fields. Temporary parser files are closed on every path.
  5. Generated storage key. The API creates a UUID job ID and stores media as {job_id}.media; the client filename is metadata only.
  6. Hash while saving. LocalMediaStore writes once, counts bytes, checks the total media budget, and returns SHA-256 plus size.
  7. Identity calculation. The cache key covers media SHA-256, pinned model revision, language, audio mode, and model profile.
  8. Atomic repository decision. PostgreSQL creates the job or reuses an idempotent request, active duplicate, or unexpired cached result.
  9. Durable handoff. Only a newly created job ID is pushed to Redis. The API returns 202 with status and result URLs.

Idempotency-Key behavior

  • Same key and same request identity: return the original job.
  • Same key and different identity: return 409 idempotency_conflict.
  • Keys remain attached to job tombstones so behavior remains stable after expiry.

Hash-cache behavior

  • Active equivalent work is reused instead of duplicated.
  • An unexpired successful equivalent result is returned immediately as the same job.
  • Ordinary hash reuse excludes failed and expired jobs. An explicitly reused idempotency key still resolves to its original job.
Why PostgreSQL is required here: pending-job admission, idempotency, and hash reuse must be decided atomically across API replicas. An in-memory dictionary cannot provide that guarantee after a restart or across processes.

Execution: supervisor, preparation, and inference

Redis delivery is deliberately lightweight. The supervisor treats a dequeued ID as a hint and asks PostgreSQL whether it can atomically claim the job.

Long-lived process

Supervisor responsibilities

  • Publish a Redis readiness heartbeat.
  • Scan for due jobs that need redispatch.
  • Recover expired PostgreSQL leases.
  • Atomically transition one job from queued to running.
  • Create a private workspace with a manifest and claimed-media copy.
  • Run model preparation, then one fresh inference child.
  • Renew the job lease while the child is alive.
  • Apply retry, terminal failure, and retention policy.
Disposable process

Inference child responsibilities

  • Read the claimed job/configuration from the private manifest.
  • Activate the OS sandbox before native library imports.
  • Select exactly one configured model profile.
  • Load the selected prepared model offline, normalize private media, and infer chunks.
  • Write a small atomic JSON outcome file.
  • Exit so native memory is reclaimed.

Inside the worker container

One long-lived supervisor, with sequential disposable preparation and inference children. These are process boundaries, not extra Compose services.

TranscriptionJobWorker.process(job_id)          ← supervisor owns DB/Redis
  └─ IsolatedJobRunner.run(claimed_job, media_path, heartbeat)
      ├─ private workspace: input.media + input.json + optional input.chunks.json
      ├─ shared deadline begins (default 1,800 seconds)
      ├─ preparation process:
      │    python -m transcription_service.attempt --prepare INPUT_MANIFEST
      │    └─ download/reuse pinned model → prepared.json → process exits
      ├─ fresh inference process:
      │    python -m transcription_service.attempt INPUT_MANIFEST RESULT_PATH
      │    └─ sandbox → offline model → decode/chunks → atomic result.json → exit
      ├─ supervisor monitors exit/deadline and refreshes heartbeat/lease
      ├─ finally: copy valid checkpoint back after child/descendants stop
      └─ return JobExecutionResult to worker lifecycle policy

Success → commit result → delete shared media/checkpoint
Retryable failure + budget → queued with backoff; retain checkpoint
Terminal/final failure → failed with retention deadline
Timeout → terminate process group; kill if still alive after five seconds

The runner polls process exit/deadline at most one second apart; the worker throttles heartbeat/lease renewal to roughly one third of the heartbeat TTL. The deadline covers preparation plus inference, with termination grace after expiry.

Why a process instead of an asyncio timeout? Cancelling a Python task does not reliably stop native codec or CTranslate2 work. The supervisor can send terminate, then kill after five seconds, providing a real wall-clock execution boundary.

Media: normalization, chunks, and model output

The worker uses one pipeline for audio files and video containers. Video frames are not decoded; PyAV selects the first audio stream.

  1. Product allowlist. Extension or MIME type must match the supported audio/video policy.
  2. Authoritative decode. PyAV/FFmpeg opens the container and requires an audio stream.
  3. Explicit normalization. Frames are resampled to signed 16-bit, mono, 16,000 Hz PCM.
  4. Decoded duration bound. PCM byte count enforces the 15-minute default even when metadata is wrong or absent.
  5. Chunk materialization. PCM is written to ordered in-memory WAV chunks; the default chunk duration is five minutes.
  6. Silence contract. Exact zero PCM returns a successful empty result with no_speech_detected without running chunk inference. Model preparation/loading already happened earlier.
  7. Per-chunk retry. Each chunk may be attempted twice inside one job attempt by default.
  8. Atomic checkpoint. Completed chunk results are replaced atomically in the private workspace. The supervisor copies the valid checkpoint back to shared storage after the child stops.
  9. Resume. A later attempt normalizes the source again, then loads its checkpoint and skips inference for completed indices.
  10. Ordered assembly. Text is joined in chunk order and segment times are offset by each chunk start.

Speech mode

Enables faster-whisper VAD filtering for normal spoken recordings and lower avoidable work.

Music mode

Disables VAD and no-speech skipping so vocals over music are less likely to be discarded.

Model profiles

faster selects pinned Whisper small; larger selects pinned large-v3. Arbitrary model IDs are not accepted from clients.

Current memory trade-off: normalization holds the bounded PCM stream in worker memory before creating chunks. That is acceptable under the current 15-minute limit; multi-hour media should use streaming durable chunks or object storage.

State: retries, recovery, and guarantee boundaries

PostgreSQL transitions control eligibility. A conditional queued-to-running update rejects ordinary duplicate deliveries; renewable leases allow abandoned work to recover. Computation is at least once, not exactly once across every crash scenario.

running→ retryable + attempts left → queued→ after backoff → claim
running→ terminal / attempts exhausted → failed→ retention → expired

Recovery cases

API stops after acceptance

PostgreSQL, Redis AOF, and the media volume already hold the work. The independent worker continues.

Redis delivery is duplicated

The second consumer cannot claim a row that is no longer eligible, so it performs no inference.

Worker dies while running

The renewable lease expires. A supervisor recovery scan returns the job to queued or marks it failed when attempts are exhausted.

Commit succeeds but enqueue fails

The persisted job is marked failed with job_enqueue_failed and retained for diagnosis; the API reports that the job infrastructure is unavailable.

Two different enqueue failure cases: a caught enqueue error during submission marks the persisted job failed and returns 503. If the process dies after commit but before it can enqueue or record that failure, a still-queued row can be redispatched by the worker scan. PostgreSQL and Redis do not share one transaction.

Operations: health, logs, and limits

Liveness

Answers whether the FastAPI process is running. It intentionally does not prove dependencies are usable.

Readiness

Requires successful PostgreSQL and Redis checks plus a non-expired worker heartbeat. It never loads the model.

Structured logs

JSON-style structured events include request IDs, routes, status, timing, job IDs, attempts, and stable error codes.

Privacy boundary: request logs do not intentionally contain transcript text, model output, uploaded bytes, or client filenames. Internal exceptions are logged; sanitized stable messages are returned to clients.

Security: container restrictions and the inference sandbox

Implemented locally

  • Localhost-only published port.
  • Non-root application user.
  • Read-only root filesystems.
  • Bounded noexec,nosuid temporary filesystem.
  • All Linux capabilities dropped.
  • no-new-privileges.
  • Generated media paths and content decoding.
  • File, duration, queue, storage, and rate bounds.
  • Pinned model revisions and locked dependencies.
  • Trusted Host and browser Origin checks; total upload receive deadline.
  • Private 0700 workspaces, 0600 files, and filtered child environments.
  • Linux Landlock/seccomp or macOS Seatbelt before native imports.
  • Inference network/command restrictions and per-process resource limits.

Required before public exposure

  • Authentication and authorization.
  • Per-account or per-API-key shared quotas.
  • A trusted reverse proxy that overwrites forwarding headers.
  • Ingress upload and idle timeouts.
  • TLS and secret management.
  • Network isolation for PostgreSQL and Redis.
  • Malware/content scanning if the threat model requires it.
Two distinct protections: the process group supplies hard cancellation; restrict_attempt() supplies OS restrictions on files, network, and execution. The inference child reads only its private files, selected cached weights, and runtime allowlist. Preparation retains network access to acquire the pinned model and exits before inference starts. The child is not a separate per-job container; container RAM/CPU limits apply to the whole worker.
Linux needs Landlock ABI 3 (kernel 6.2+) and libseccomp2; macOS uses Seatbelt. Unsupported platforms or setup errors fail before decoding. This is a CPU policy; GPU devices require a separately reviewed access policy. See Security Hardening for exact rules and probes.

The replaceable interfaces

JobRepository, JobBroker, MediaStore, and JobRunner define infrastructure/execution operations. MediaNormalizer and Transcriber define the blocking media/model operations. Production supplies PostgreSQL, Redis, filesystem, process, PyAV, and faster-whisper implementations; tests can inject deterministic replacements.
