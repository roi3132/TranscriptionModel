Handoff brief

Historical plan: Estimates, phase checklists, and verification counts below preserve development milestones. Later improvements add local media playback, processing feedback, real infrastructure tests in CI, and a small accuracy evaluation. For the current implementation and verification, use the architecture reference, execution guide, and README.

Phases 0–8 are implemented. The local stack now covers durable jobs, reliability, explicit media normalization, resumable chunking, exports, and the minimal recovery-aware UI.

Primary outcome: A reviewer can clone the repository, run one Docker command, submit an audio or video file, receive a durable job ID, and retrieve a Hebrew or English transcription with timestamped segments after an independent worker completes it.

Instructions for the coding agent

  • Work phase-by-phase and run the listed checks after every phase.
  • Prefer established libraries and standard-library functions over custom infrastructure.
  • Keep model-specific code behind the Transcriber interface.
  • Record any changed assumption in the README before implementing around it.
  • Do not silently expand the scope.

Deferred beyond phases 6–8

  • No managed cloud dependency: Redis, PostgreSQL, media storage, API, and workers run locally in Docker Compose.
  • No Kubernetes, managed S3 requirement, accounts, billing, or complex user-owned history.
  • No translation, diarization, LLM summaries, transcript editor, PII redaction, URL ingest, or live streaming.
  • No React build chain; use a small static page only.

Runtime architecture

The API is model-free: PostgreSQL owns job state, Redis hands off IDs, a supervisor owns reliability policy, and a disposable child owns one native inference attempt.

Request lifecycle

  1. Reject an obviously oversized request using Content-Length when present.
  2. Receive the upload through FastAPI UploadFile; never use the client filename as a path.
  3. Check the actual uploaded size and configured media allowlist.
  4. Persist and hash the upload, commit its PostgreSQL job, enqueue its ID, and return 202.
  5. The supervisor atomically claims the job and launches one terminable child process.
  6. The child normalizes the first audio stream to 16 kHz mono chunks and loads only the selected model.
  7. Fully consume faster-whisper's lazy segment generator, checkpoint chunks, and assemble the result.
  8. Persist the result, delete successful source media, and serve status or exports independently.
Worker model lifecycle: Each isolated attempt loads the selected model from the shared Hugging Face cache. FastAPI never loads model weights; readiness depends on PostgreSQL, Redis, and a live worker heartbeat.
Durable lifecycle: Compose persists and hashes the upload before enqueueing. The supervisor atomically claims a renewable lease, launches a terminable child, retries transient failures, recovers stale claims, and expires retained artifacts. Readiness checks PostgreSQL, Redis, and a live worker heartbeat without invoking inference.

GET/health/live

Returns success when the HTTP process is alive. It must not invoke the model.

GET/health/ready

Checks PostgreSQL, Redis, and an unexpired worker heartbeat without invoking inference.

Error envelope

{
  "error": {
    "code": "unsupported_media",
    "message": "The uploaded file could not be decoded.",
    "request_id": "01J..."
  }
}

Log the exception and context server-side, but do not expose stack traces, local paths, or dependency error strings to clients.

Implemented contract: POST /v1/transcriptions always returns 202 Accepted, a job ID, and a Location header. GET /v1/transcriptions/{job_id} returns queued, running, succeeded, failed, or expired. GET /v1/transcriptions/{job_id}/result returns JSON by default and supports TXT, SRT, and VTT through the format query parameter.
Phase 7 contract: Status also reports attempts, maximum attempts, next retry time, terminal code/message, and expiry. Hash-equivalent active/successful jobs are reused; successful media is removed immediately; retained results and failed media become expired on schedule.

Testing strategy

Fast suite — always run

  • Configuration parsing and invalid combinations.
  • Health before/after job infrastructure and worker readiness.
  • API contract using a deterministic fake transcriber.
  • Upload size, MIME/container mismatch, corrupt media, and missing audio.
  • Language validation, Hebrew Unicode serialization, and segment mapping.
  • Model errors, overload behavior, request IDs, and resource cleanup.
  • 16 kHz mono normalization, silence warnings, chunk retry/resume, and ordered assembly.
  • Local rate windows plus JSON, TXT, SRT, and VTT rendering.

Slow suite — explicit opt-in

  • Download and load the configured Hugging Face model.
  • Transcribe one short known audio sample.
  • Assert language, non-empty text, ordered timestamps, and plausible duration.
  • Do not run this suite in normal CI; model download and output depend on hardware.

Definition of done

The four groups below cover the completed durable asynchronous-only Phases 6–8 stack.

Functional

  • Audio and video with audio are accepted through one endpoint.
  • Hebrew and English work with auto-detection or explicit language codes.
  • Response includes full text, language metadata, duration, processing time, and timestamped segments.
  • Browser UI displays Hebrew RTL and English LTR correctly.

Operational

  • The API stays model-free; readiness reflects PostgreSQL, Redis, and a live worker heartbeat.
  • Uploads are bounded and closed on every path.
  • Inference cannot block the event loop or run without a concurrency limit.
  • Successful source media is deleted immediately; failed media and results follow configured retention.

Quality

  • Lint, format, type, and fast tests pass locally and in CI.
  • Errors are stable, useful, and do not leak internal details.
  • The real model and Docker flows have been smoke-tested.
  • Code is organized around boundaries, not speculative abstractions.

Delivery

  • Repository is cloneable and contains no model weights or secrets.
  • README commands work on a clean CPU-only environment.
  • Assumptions, shortcuts, security limits, and future architecture are explicit.
  • Git history shows coherent product increments.
Phases 6–8 complete: The stack proves durable asynchronous handoff, retries and hard deadlines, deduplication, crash recovery, retention, readiness, 16 kHz mono normalization, explicit silence, resumable chunking, rate limiting, exports, and UI reload recovery. Real-model quality remains an explicit opt-in smoke test.
